# 阶段 5 · 对账与交付

## 1. 反向审查：只收能落到行号的意见

自查方式：让审查者（人或 AI）扮演**挑刺的人**，四条输出缺一不可，且**每条必须给文件名与行号**。给不出行号的评价一律退回。

| 输出块 | 要求 | 不合格示例 |
|---|---|---|
| 逐处原理 | 说清这段为什么这么写，以及换一种写法会怎样 | 「这里写得不错」 |
| 致命风险 | 空指针、事务失效、资源未释放、越权、状态漏校验 | 「注意异常处理」 |
| 性能瓶颈 | N+1 查询、无索引条件、循环内查库、一次性全表加载 | 「可以优化」 |
| 重构建议 | 给出改前/改后代码片段 | 「建议分层更清晰」 |

### 本项目必须逐条过的审查点

| # | 审查点 | 怎么查 | 典型错法 |
|---|---|---|---|
| R1 | 状态守卫是否覆盖全部迁移 | 对照 `state-machine.json` 的 `transitions`，逐个方法看前置校验 | 只校验了"不是终态"，没校验"必须是某个态" |
| R2 | 双闸权限 | 每个带 id 的写接口，服务层是否有归属比对 | 只在 Controller 加了 `@RequireRole` |
| R3 | 留痕完整性 | `grep writeLog`，与 `audit-actions.json` 双向比对 | 改期写了，加物料没写 |
| R4 | 事务边界 | 跨表写入是否同事务；方法内是否有远程调用 | 上传文件在事务内做 IO |
| R5 | 错误码语义 | 409 用于状态冲突，403 用于权限，不要混 | 权限失败返回 400 |
| R6 | 错误信息可用性 | 是否带上了当前状态/剩余数量 | 「操作失败」 |
| R7 | 文件安全 | 白名单 + `normalize()` + `startsWith` | 只做了 `contains("..")` |
| R8 | 前端状态标签 | 是否有页面自写状态判断 | 详情页手写中文映射 |
| R9 | 敏感信息 | 密码摘要算法、密钥位置、日志是否打印敏感字段 | `log.debug` 打印 token |
| R10 | 已知限制是否如实列出 | README 的"已知限制"与实际是否一致 | 声称有分页其实没有 |

### 一个真实的审查结论长什么样

> `TaskService.java:133` `uploadVersion` 在 `@Transactional` 方法内做了 `Files.copy` 落盘。文件写入不在事务内，事务回滚后磁盘会残留孤儿文件；同时慢盘会拉长事务持有时间。建议：先落盘再开事务，或把落盘移到事务提交后（`TransactionSynchronization`），并为孤儿文件加清理任务。

这才叫可执行的意见。

## 4. 答辩/汇报话术

评审最容易问的三个问题，提前准备答案，**用机制回答，不要用形容词**：

**Q：你怎么保证越权操作被拦住？**
> 两道闸。入口用 `@RequireRole` 按权限矩阵挡角色；服务层用 `assignee_id` 比对挡数据归属。这两层都由 `permissions.json` 声明，`check-contract.ps1` 的 G4 会核对契约、注解、服务层校验三方是否一致。验收用例里有 5 条越权断言。

**Q：状态会不会乱转？**
> 状态全集和迁移表在 `state-machine.json` 里声明，代码用实体常量引用，前端标签同源生成。G5 会检查代码里出现的状态字面量是否都在契约内、前端是否漏了标签。跳步和重复操作在验收里有 409 断言。

**Q：改完了怎么证明没改坏？**
> 两层。静态层 G2/G3 对账 DDL、实体、Mapper、接口文档、前端 API 层是否仍一致；运行时层 `check-api.ps1` 跑 31 条真实 HTTP 断言。两条命令、两个退出码，不是靠人工翻代码。

**Q：这套东西的价值是什么？**
> 把"我记得改了"变成"脚本证明改了"。文档和代码之间、代码和数据库之间、契约和权限之间，任何一处漂移都会变成一条带文件行号的 FAIL。

## 5. 交付后的一轮回归

任何修改后固定三步，不要跳：

1. `check-contract.ps1` —— 静态对账；
2. 重启后端 + `check-api.ps1` —— 运行时验收；
3. 用 4 个演示账号各登一次，确认菜单与按钮随角色变化（这一条脚本查不了，必须人看）。

第 3 步不能省：脚本能证明接口拦住越权，证明不了界面把不该出现的按钮藏起来了。

## 6. 反模式收尾表

| 反模式 | 代价 | 替代做法 |
|---|---|---|
| 让 AI 一次性生成整个项目 | 得到无法维护的代码，且没有一处能追溯到需求 | 一轮一个 flow |
| 改代码不改契约 | 下次会话 AI 会按旧契约写，产生第二套逻辑 | 改代码前先改契约 |
| 用测试迁就实现 | 红灯变绿但业务错误仍在 | 改 `expect` 必须能说出业务规则变了 |
| 留痕写在 Controller | 事务边界不同，回滚后日志残留 | 留痕与业务同方法同事务 |
| 只在 Controller 做鉴权 | 设计人员可操作他人任务 | 双闸 |
| 文档写完就不再碰 | 文档变成历史文件，新人按它开发会错 | 每次改动同步，改不动就删掉那一段 |
