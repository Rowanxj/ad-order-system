# 答辩演示脚本（对应课程「最终演示结构」9 条）

> 用法：答辩前通读一遍；演示时照着「先说什么 → 点什么 → 给什么证据」走。
> 全程约 12–15 分钟，可按时间裁剪（每节末尾标了耗时）。

---

## 0. 开场前 10 分钟准备

```powershell
# 1) 备份一次数据库（万一演示中改坏，能立刻恢复）
powershell -ExecutionPolicy Bypass -File scripts\backup-db.ps1

# 2) 起后端（带文件日志）
powershell -ExecutionPolicy Bypass -File scripts\start-backend.ps1

# 3) 起前端
cd frontend; npm run dev
```

打开三个窗口并排：

| 窗口 | 内容 | 用途 |
|---|---|---|
| 左 | 浏览器 <http://localhost:5173> | 点界面 |
| 中 | Navicat（已连 `ad_order_system`） | 现查数据库 |
| 右 | 浏览器 F12 → Network 面板 | 看接口原始返回 |

> 演示前**重置演示数据**（可选）：重新导入 `sql/data.sql`，保证订单是干净的 3 笔。

## 1. 企业与问题（60 秒，逐字稿）

> "广告制作公司接的是客户的**宣传物料委托**：一张海报、一个展架、一本菜单。
> 这类业务有三个特点：**跨岗位**（客户经理谈、负责人排、设计师做）、**多轮返工**（客户改颜色改文案）、**必须留痕**（改期、加项都要说得清是谁定的）。
>
> 但公司现在的做法是微信传图 + 口头传达。出问题时三个问题说不清：
> **谁改的？改之前是什么？客户到底确认的是第几版？**
>
> 我做的系统就是把这笔单子的全过程管起来——重点是**状态不能乱转、权限不能越、每一步留痕**。"

**（计时：1 分钟）**

---

## 2. 岗位、业务对象、核心规则（2 分钟）

> "三个岗位，职责互斥：

| 岗位 | 能做什么 | 不能做什么（系统强制） |
|---|---|---|
| 客户经理 | 登记客户、建单、记客户意见、记客户确认 | 不能确认订单、不能分派 |
| 业务负责人 | 确认订单、分派/改派、交付 | 不能记客户确认 |
| 设计制作人员 | 只看自己的任务，开始设计、上传稿件 | 看不到别人的任务，不能确认任何东西 |

> 业务对象是 4 层：**客户 → 物料订单 → 物料任务 → 设计版本 / 客户意见**，全部动作再落到 1 张 `operation_log`。

> 两条核心规则：
> 1. **上传设计稿 ≠ 客户确认**。上传只是"提交待确认"，只有客户经理能记录客户确认结果。
> 2. **确认后不能覆盖，只能追变更**。订单确认后改期、加物料，都是追加一条变更记录，写明**原值 → 新值**。"

**（这条是评分点 2，务必指到界面上的状态标签）**

## 3. 完整业务链路（3 分钟，四个账号轮着登）

> 演示前记住：**每次切换账号都要真的退出登录**，让老师看到菜单变化。

| 步 | 账号 | 操作路径 | 说什么 |
|---|---|---|---|
| 1 | `sales` | 订单管理 → 新建订单 → 填客户/标题 + 2 项物料 → 提交 | "客户经理登记，订单进入**待确认**" |
| 2 | `manager` | 打开该单 → 「确认订单」 | "负责人确认物料清单，进入**进行中**" |
| 3 | `manager` | 任务行 → 「分派」→ 选李文静 | "分派只改负责人字段，**状态不变**（仍是待开始）" |
| 4 | `designer1` | 我的设计任务 → 「开始设计」→ 进详情上传一张图 | "设计人员开始做，上传后任务变**待客户确认**" |
| 5 | `sales` | 订单详情 → 该任务「详情」→「客户已确认当前版本」 | "客户认可，客户经理代记，任务**已确认**" |
| 6 | `manager` | 另一项任务也走到确认 → 「订单交付」 | "全部确认后整单才能交付" |

**强调一句**：每一步都会在订单详情的右侧「操作历史」里出现一条带姓名和角色的记录。

**（评分点 3）**

### 3.1 工作台与异常管理（30 秒，可选）

| 步 | 账号 | 操作路径 | 说什么 |
|---|---|---|---|
| 7 | `manager` | 登录后默认进「工作台」→ 看指标卡 | "角色化工作台：待确认、待分派、待客户确认、逾期、进行中一屏看清" |
| 8 | `manager` | 点「异常管理」→ 切「任务逾期 / 待分派 / 待客户确认」 | "异常不是靠人翻订单找，而是按类型聚合；点一条能直接分派、改期或进详情" |

> 工作台的指标卡可以直接跳到 `/orders?overdue=true` 或 `/exceptions?type=TASK_UNASSIGNED`，路由参数会被列表页读取并重新查询。

## 4. 正常 / 异常 / 越权 三个场景（2 分钟）

### 正常场景
第 3 节走的就是正常链路，不用重复演示，说一句"刚才那条就是"。

### 异常场景（选最强的）
> "订单里还有 2 项没确认，负责人点交付——"

**操作**：`manager` 打开该单 → 点「订单交付」→ 弹窗点 **「仍然提交」** → 顶部出现红字：
**「还有 2 项物料任务未确认，整笔订单不能交付」**

> "这是后端 `409` 返回的原文。前端只是提前提示，不隐藏按钮、也不做最终判定；
> 点『仍然提交』后，真正的拦截来自服务端——因为**规则只有一份，写在服务端**。"

### 越权场景（选最直观的）
> "设计人员想操作别人的任务——"

**操作**：用 `designer2` 打开一个分派给 `designer1` 的任务详情 → 页面提示 **403**；或直接在地址栏访问该任务链接。

> "越权有两道闸：入口的 `@RequireRole` 挡角色，服务层的 `assignee_id` 比对挡数据归属。
> 只做第一道的话，设计人员仍能操作他人任务。"

**（评分点 4）**

## 5. 一次状态变化的三处证据（2 分钟，**最加分的一节**）

选「确认订单」这个动作，三处同时给证据：

### ① 页面
`manager` 点「确认订单」→ 订单状态从「待确认」变「进行中」，按钮区变成「订单交付」。

### ② 接口（F12 → Network）
点之前先按 F12 打开 Network，再点按钮，找到请求：

```
PUT /api/orders/1/confirm     →  200
Response: {"code":0,"message":"success","data":null}
```

再演示一次失败：对**已确认**的订单再点一次（或直接调接口），返回

```json
{"code":409,"message":"订单当前状态不允许执行该操作（当前状态：IN_PROGRESS）"}
```

### ③ 数据库（Navicat 现查）

```sql
-- 状态确实变了
SELECT id, order_no, status, updated_at FROM material_order WHERE id = 1;

-- 并且留下了一条留痕（谁、什么角色、什么时候、改了什么）
SELECT action, action_text, detail, operator_name, operator_role, created_at
FROM operation_log WHERE order_id = 1 ORDER BY id DESC LIMIT 3;
```

> "三处对得上：**页面变了、接口返回成功、数据库有状态和留痕**。
> 如果只改数据库不改页面，说明前端在骗人；如果只改页面不改数据库，说明刷新就没了。
> 三处一致才算这笔操作真的发生。"

**（评分点 5，这一节讲完老师通常会点头）**

## 6. 一次 AI 参与开发的任务与验证过程（2 分钟）

> 我们不是"让 AI 写完就信"。举一个真实例子。

**背景**：让 AI 写一个"契约体检脚本"，检查状态机、权限、留痕是否和代码一致。

**过程**：
1. 先让 AI 把规则写成机器可读的 JSON 契约（状态机 9 个状态 / 8 条迁移、权限 31 条路由、留痕 12 个动作码）；
2. 让 AI 写脚本读契约，和 Java 代码、Mapper XML、前端 api 层逐项对账；
3. **关键一步**：我不信它"能查",于是**故意注入 5 类缺陷**验证它是不是真的会报错——

| 注入的缺陷 | 脚本是否报出 |
|---|---|
| 前端把 `REVISION` 写成 `REVISING` | ✅ 报「状态在前端映射中缺失」 |
| 删掉确认订单的角色注解 | ✅ 报「角色不一致：契约=[MANAGER] 代码=[]」 |
| 留痕动作码拼错 | ✅ 报「动作码未注册」 |
| DDL 把 `spec` 改名 | ✅ 报「实体无对应字段」+「INSERT 用了不存在的列」 |
| 前端调用不存在的接口 | ✅ 报「后端不存在的接口」 |

**结论**：5 条全部精确报出，并定位到文件行号。
**现在的状态**：这套门禁每次改完都跑，当前 `FAIL=0 WARN=0`；另有 66 条接口级自动验收全绿，单测 80 条全绿。

> 过程中也发现过 AI 的错：它一度把「分派」写成会改变状态，被状态机契约拦下；
> 还有一次把表格竖线替换成了空格，是我抽查文档时发现的——**AI 产出必须验证**。

**（评分点 6：重点说"怎么验证的"，不是"AI 多厉害"）**

## 7. 关于挑战赛道（10 秒，一句话带过）

> "我们参加的是**常规赛道**，第 7 条（AI 有依据回答 / 依据不足 / 模型失败三态）不适用。
> 系统里没有让大模型参与业务判断，所有规则都是确定性代码。"

## 9. 未完成、已知限制、为什么不能直接投产（1.5 分钟）

> 我明确知道它的边界在哪：

| 类别 | 现状 | 为什么不能直接生产 |
|---|---|---|
| 密码策略 | PBKDF2 + 随机盐（已达标），但**没有登录失败锁定、没有验证码、没有二次验证** | 挡不住撞库与暴力破解 |
| 权限 | 双闸（角色 + 数据归属），但**没有操作审计的独立日志系统** | 出了内鬼查不全 |
| 并发 | 状态迁移用条件更新，取号/版本号用唯一索引兜底，**但没有做过压测** | 真实并发量下未验证 |
| 文件 | 存本机磁盘，**没有对象存储、没有病毒扫描、没有容量配额** | 单机故障即丢稿 |
| 分页 | 只有订单列表分页，客户与"我的任务"全量返回 | 数据量上千会拖慢 |
| 生命周期 | **没有数据归档与清理策略**，日志与版本文件会无限增长 | 长期运行会撑爆磁盘 |
| 合规 | 客户联系方式未脱敏、无数据导出与删除接口 | 不满足个人信息保护要求 |
| 部署 | 单机 + 手工启动，**没有容器化、没有健康检查、没有监控告警** | 挂了没人知道 |

> 一句话总结：**这是一个"把业务规则做对了"的教学级系统，不是一个能直接上线的生产系统。**
> 差的那部分不是写不出来，是生产环境需要的运维、安全、合规配套，超出课程范围。

**（评分点 9：主动说限制，比被问出来更得分）**

## 附录 A：常用 SQL（Navicat 里现查，答辩随取）

> **怎么用**：Navicat 连上 MySQL（`localhost:3306`，用户 `root`，密码是你本机 MySQL 口令）→ 双击 `ad_order_system` → 点上方「查询」→「新建查询」→ 粘贴一条 SQL → 点「运行」。结果会出现在下方表格。
>
> 如果运行时报 `1046 - No database selected`，在 SQL 最上面加一行 `USE ad_order_system;`，选中整段再运行。
>
> 下面以**演示订单 901、演示任务 1** 为例。换订单时，只改 SQL 里的 `901`；换任务时只改 `1`。

```sql
-- 1. 订单全貌：状态 + 物料数 + 已确认/未确认数
SELECT o.id, o.order_no, c.name AS 客户, o.title, o.status, o.deadline,
       (SELECT COUNT(*) FROM material_task t WHERE t.order_id=o.id) AS 物料数,
       (SELECT COUNT(*) FROM material_task t WHERE t.order_id=o.id AND t.status='CONFIRMED') AS 已确认,
       (SELECT COUNT(*) FROM material_task t WHERE t.order_id=o.id AND t.status<>'CONFIRMED') AS 未确认
FROM material_order o JOIN customer c ON c.id=o.customer_id
WHERE o.deleted=0 ORDER BY o.id DESC;

-- 2. 订单 901 的任务与分派（409 演示时，这里应看到 2 项未确认）
SELECT t.id, t.name, t.status, u.real_name AS 设计人员,
       (SELECT COUNT(*) FROM design_version v WHERE v.task_id=t.id) AS 版本数
FROM material_task t LEFT JOIN sys_user u ON u.id=t.assignee_id
WHERE t.order_id=901 ORDER BY t.id;

-- 3. 订单 901 的留痕（证明“哪些动作真的发生了”；409 失败后不应出现 ORDER_COMPLETED）
SELECT action, action_text, detail, operator_name, operator_role, created_at
FROM operation_log WHERE order_id=901 ORDER BY id DESC;

-- 4. 任务 1 的归属（403 证据：assignee_id=3 是 designer1，不是 designer2）
SELECT t.id, t.name, t.status, t.assignee_id, u.username, u.real_name
FROM material_task t LEFT JOIN sys_user u ON u.id=t.assignee_id
WHERE t.id=1;

-- 5. 账号与状态（1启用 0停用 2待启用；designer1=3，designer2=4）
SELECT id, username, real_name, role, status FROM sys_user ORDER BY id;
```

### 答辩时怎么配合

| 演示点 | 先查什么 | 操作后查什么 | 你要说的一句话 |
|---|---|---|---|
| 409 交付被拦 | 第 1、2 条：订单 901 是「进行中」，未确认=2 | 再查第 1、2、3 条：状态仍是「进行中」，未确认仍是 2，且没有 `ORDER_COMPLETED` | “失败的操作没有改变数据库，也没有留下成功留痕。” |
| 状态变化留痕 | 第 1、3 条：确认前是「待确认」，没有 `ORDER_CONFIRMED` | 点「确认订单」后再查：状态变「进行中」，第 3 条出现 `ORDER_CONFIRMED` | “页面状态变了，数据库状态和留痕也同步变了。” |
| 403 越权 | 第 4、5 条：任务 1 的 `assignee_id=3`（designer1），designer2 的 id 是 4 | 用 designer2 打开任务 1，页面 403 | “任务归属在数据库里写得很清楚，服务层就是按这个字段拦的。” |

## 附录 B：最可能被问的 5 个问题

| 问题 | 怎么答（一句话） |
|---|---|
| 为什么订单和任务要分两张表？ | 一笔订单有多个物料，每个物料独立分派、独立出稿、独立确认，进度不一样 |
| 为什么"确认"和"上传"要分开？ | 上传只是提交，客户口头同意只有客户经理知道，必须由人显式记录，否则无法追责 |
| 两个人同时确认会怎样？ | 数据库条件更新，先到的成功，后到的返回 409「状态已被其他人改变」 |
| 为什么不用 Spring Security？ | 演示项目链路要短、可读；生产会换成 Security 或网关鉴权 |
| 代码有多少是 AI 写的？ | 骨架和大部分实现是 AI 生成，**规则建模、验收用例、缺陷发现与修复判定是人做的**；AI 的产出全部由脚本、66 条接口用例和 80 条单测验证 |
