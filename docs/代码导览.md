## 一、30 秒讲清架构（先给地图，别让老师自己找）

> "后端是 **Controller → Service → Mapper** 三层：Controller 只收参数和权限注解，Service 放业务规则与事务，Mapper 只管 SQL。
> 前端是 **Vue 3 单页应用**，所有请求都走 `src/api/` 一层封装，页面不直接发请求。
> 数据有 7 张表：客户 → 订单 → 物料任务 → 设计版本 / 客户意见，所有关键动作再落一张 `operation_log`。"

## 二、五个必看文件（按这个顺序讲，5 分钟）

### ① `ApiController.java` —— 接口入口

**看哪里**：随便挑一个方法，比如 `confirmOrder`

```java
@PutMapping("/orders/{id}/confirm")
@RequireRole({"MANAGER"})
public Result<Void> confirmOrder(@PathVariable Long id) {
    orderService.confirm(UserContext.get(), id);
    return Result.ok();
}
```

**怎么讲**：
> "Controller 只有三行：**路由、权限注解、调 Service**。业务判断一行都没有——因为控制器写业务，规则就会散落在各处。"

---

### ② `OrderService.confirm()` —— 状态机的落点（最重要，重点讲这个）

**找这段**（约 136–150 行）：

```java
MaterialOrder order = requireExists(id);
checkTransition(order.getStatus(), MaterialOrder.PENDING_CONFIRM, "订单");
if (taskMapper.selectByOrderId(id).isEmpty()) {
    throw new BusinessException("订单还没有物料任务，无法确认");
}
if (orderMapper.updateStatus(id, MaterialOrder.PENDING_CONFIRM, MaterialOrder.IN_PROGRESS) == 0) {
    throw new BusinessException(CONFLICT, "订单状态已被其他人改变，请刷新后重试");
}
writeLog("ORDER", id, id, "ORDER_CONFIRMED", ...);
```

**怎么讲**（四步固定说法）：
> "状态变更都是这个四步：**读现状 → 校验前置态 → 写入目标态 → 写留痕**。
> 关键是第三步：`updateStatus(id, from, to)` 是**条件更新**，SQL 里带 `WHERE status = '待确认'`。
> 如果两个人同时点确认，第二个人的影响行数是 0，直接返回 409，**不会出现后写的覆盖先写的**。
> 这就是为什么不用「先查再改」——查完到你写进去之间，别人可能已经改了。"

**如果老师问"为什么不用乐观锁 version 字段"**：
> "状态本身就是最合适的版本号。多一个 version 列还要维护它，而状态在每次迁移时必然会变。"

### ③ `TaskService.requireAssignee()` —— 双闸权限

**找这段**（约 317 行附近）：

```java
private void requireAssignee(MaterialTask task, LoginUser user) {
    if (!user.getId().equals(task.getAssigneeId())) {
        throw new BusinessException(FORBIDDEN, "设计人员只能处理分派给自己的任务");
    }
}
```

**怎么讲**：
> "越权有两道闸：入口的 `@RequireRole` 挡**角色**，这个方法挡**数据归属**。
> 只做第一道的话，设计人员虽然进不来「分派接口」，但能操作**别人的任务**——因为角色对、数据不对。"

### ④ `MaterialTaskMapper.xml` 的 `listFilter` —— SQL 层的数据范围

**找这段**：

```xml
<if test="viewerRole == 'DESIGNER'">
    AND EXISTS (SELECT 1 FROM material_task t WHERE t.order_id = o.id AND t.assignee_id = #{viewerId})
</if>
```

**怎么讲**：
> "设计人员只能看到含自己任务的订单，这个过滤放在 **SQL 里**，不是查出来再在 Java 里筛。
> 因为查出来再筛，数据已经进内存了，而且分页的 total 会算错。"

**看哪里**：随便翻一页，比如 G4 权限对账那段

## 三、三个最可能被追问的问题（背下这三句）

| 问题 | 一句话回答 |

| 这段代码是你写的还是 AI 写的？ | "骨架和大部分实现是 AI 生成，**规则建模、验收用例、缺陷发现与修复判定是我做的**。AI 的产出全部由 43 条接口用例和 8 道静态检查验证。" |

## 四、关于那个 skill（30 秒，放在"AI 协作"环节讲）

**是什么**：一套**给 AI 的操作手册 + 自动检查脚本**，不是一个功能模块。

**怎么讲**：
> "我用 Claude/DSH 这类 AI 写代码，但 AI 有两个毛病：**会忘规则、会自信地写错**。
> 所以我把「状态机、权限矩阵、留痕动作」写成机器能读的 JSON 契约，再写脚本每次改完自动对账。
> 同时给它一份流程手册（就是那个 skill），规定「先写契约再写代码、一次只做一个场景」。
> 这样 AI 换多少次、人换谁来接手，规则都不会跑偏。"

**如果老师问"这有什么用"**：
> "这次开发里 AI 至少犯过 4 个错误：把分派实现成会改状态、上传文件写在事务里、取号用 COUNT+1 会重号、文档表格被它批量改坏。
> 前面三个都被契约和测试拦住了，最后一个是我抽查发现的——所以我加了文档占位符和结构检查。"

**不要说**："我做了个 AI 工具"（夸大）、"这是自动生成的"（显得没参与）。
**要说**："我给 AI 立了规矩，并用脚本验证它遵守了没有。"

## 五、兜底话术（被问到你真没看过的代码）

不要愣住，也不要编。按这个模板：

> "这段是 AI 生成的模板代码（比如实体类、Mapper 的 CRUD），作用是 X。
> 我重点核对的是**它和契约是否一致**——字段名对得上 DDL、接口路径对得上文档，这由脚本检查。
> 至于这一行的具体写法，我现在不能保证完全准确，但可以确定它没有绕过状态机和权限。"

**为什么这样答**：
- 承认边界（不装懂）
- 立刻给出**你能保证的部分**（契约一致性、状态机未被绕过）
- 把话题拉回你的强项
