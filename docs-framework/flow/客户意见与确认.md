# 场景：客户意见与客户确认

## 1. 触发入口

- 页面：`/tasks/:id` 的 [记录修改意见]、[记录客户确认]（客户经理）
- 前置：任务状态必须是 `PENDING_CONFIRM`

## 2. 接口链路

1. `POST /api/tasks/{id}/feedbacks` —— 记录意见
2. `PUT /api/tasks/{id}/confirm` —— 记录客户确认

## 3. 数据变更

记录意见：

1. 读任务，校验 `status = PENDING_CONFIRM`，否则 409
2. 取轮次 `MAX(round_no)+1`
3. `INSERT revision_feedback(content)`
4. `UPDATE material_task SET status='REVISION'`
5. 写 `FEEDBACK_RECORDED`（detail 含轮次与内容摘要，超长截断到 50 字）

记录确认：

1. 读任务，校验 `status = PENDING_CONFIRM`，否则 409
2. `UPDATE material_task SET status='CONFIRMED'`
3. 写 `TASK_CONFIRMED`

## 4. 页面反馈

| 结果 | 反馈 |
|---|---|
| 记录意见成功 | 意见列表追加一轮，状态变"修改中"，出现"等待新版本"提示 |
| 记录确认成功 | 状态变"已确认"，时间线追加"客户确认"，操作按钮消失 |
| 409 | 显示当前状态原因，刷新详情 |
| 403 | 设计人员无此按钮；即便直接调接口也被注解拦下 |

## 5. 异常与边界

| 场景 | 预期 | 处理 |
|---|---|---|
| 设计人员调用确认接口 | 403 | `@RequireRole({"SALES"})` |
| 客户经理在自己没被分配的任务上操作 | 允许 | 客户经理职责是代客户记录，不要求归属 |
| 空意见内容 | 400 | DTO `@NotBlank` |
| 任务还没上传就记录确认 | 409 | 状态必须是 `PENDING_CONFIRM` |
| 意见超过 500 字 | 400 | DTO `@Size(max=500)` |
| 同一任务重复记录确认 | 409 | 第二次状态已变 `CONFIRMED` |

## 6. 语义说明（最容易实现错的地方）

- "客户确认"是**业务事件**，不是"文件上传成功"。系统不提供客户登录入口，客户的口头确认由客户经理代记，因此该动作必须留下"谁记录的"痕迹，便于事后追责。
- 记录意见后任务一定回到"修改中"，不允许同一条意见后又直接确认——必须先有新版本（`VERSION_UPLOADED`）才能再进入"待客户确认"。
