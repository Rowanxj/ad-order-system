# 场景：订单交付与确认后变更

## 1. 触发入口

- 页面：`/orders/:id` 的 [交付订单]（负责人）、[修改截止日期] / [新增物料]（客户经理）
- 前置：交付要求订单 `IN_PROGRESS` 且全部任务 `CONFIRMED`；改期/新增物料要求订单未结束

## 2. 接口链路

1. `PUT /api/orders/{id}/complete` —— 交付
2. `PUT /api/orders/{id}/deadline` —— 改整单截止日
3. `PUT /api/tasks/{id}/deadline` —— 改单项物料截止日
4. `POST /api/orders/{id}/tasks` —— 确认后新增物料

## 3. 数据变更

交付：

1. 读订单，校验 `status = IN_PROGRESS`，否则 409
2. `SELECT COUNT(*) FROM material_task WHERE order_id=? AND status<>'CONFIRMED'`
3. 计数 > 0 → 409，消息带剩余数量
4. `UPDATE material_order SET status='COMPLETED'`
5. 写 `ORDER_COMPLETED`

改期（整单 / 单项）：

1. 读订单，若 `COMPLETED`/`CANCELLED` → 409
2. 单项改期还需校验该任务未 `CONFIRMED`
3. `UPDATE ... SET deadline=?`
4. **仅当订单为 `IN_PROGRESS`** 时写日志：`ORDER_DEADLINE_CHANGED` / `TASK_DEADLINE_CHANGED`
   - `detail` 必须形如 `原截止日期 2026-12-20 → 新截止日期 2026-12-28（客户同意后变更）`

新增物料：

1. 读订单，状态必须是 `PENDING_CONFIRM` 或 `IN_PROGRESS`，否则 409
2. `INSERT material_task(status='PENDING')`
3. 若订单已 `IN_PROGRESS`，写 `TASK_ADDED`（detail 含物料名、数量、截止日期）

## 4. 为什么"确认后变更要留痕"

订单一旦被负责人确认，物料清单与时间是**对客户的承诺**。此后任何改动都不是修 bug，而是改合同——必须能回答：

- 谁提出、谁同意、什么时候改的？
- 改之前是什么（原值）？

因此 `detail` 不允许只写"修改截止日期"，必须写原值与新值。这条由 `contracts/audit-actions.json` 的 `detailPattern` 标注，审查时按它核对。

## 5. 页面反馈

| 结果 | 反馈 |
|---|---|
| 交付成功 | 状态变"已交付"，全部操作按钮消失，时间线追加"订单交付" |
| 未全部确认就交付 | 409，消息形如"还有 2 项物料任务未确认，整笔订单不能交付"，页面高亮未确认任务行 |
| 改期成功 | 截止日期更新；若订单进行中，时间线出现变更记录 |
| 已结束订单改期 | 409，按钮本应对已结束订单隐藏 |

## 6. 异常与边界

| 场景 | 预期 | 处理 |
|---|---|---|
| 订单有 0 项任务就交付 | 409 | 计数逻辑天然覆盖（0 未确认但也没有可交付内容），实际由"未确认=0 且任务数=0"提示 |
| 确认后新增物料但一直未分派 | 整单永远不能交付 | 这是正确的业务约束，验收用例 C26 专门断言 |
| 任务已确认再改期 | 409 | 服务层校验任务状态 |
| 订单已交付再改期 | 409 | 服务层校验订单状态 |
| 交付并发（两人同时点） | 后到者 409 | 状态在事务内重新读取校验 |
